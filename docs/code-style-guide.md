# MathArts 通用代码风格指南

本文件定义 MathArts 仓库之间可以共享的最低代码质量约定。它不是某种语言的完整 Style Guide，也不替代项目仓库中的 formatter、linter、类型检查配置和本地开发说明。

当本文件与目标仓库的自动化配置或明确文档不一致时，以目标仓库的本地规则为准；组织级边界、安全要求和已经接受的架构决定除外。

## 1. 基本原则

代码应当：

- 优先遵循目标语言和目标仓库已经采用的惯例；
- 使用仓库现有的格式化、Lint、类型检查和测试工具；
- 保持职责边界清晰，避免为了复用而引入跨层依赖；
- 优先选择清晰、可验证、可维护的实现，而不是技巧性写法；
- 对公共行为、边界条件和错误路径提供适当测试；
- 不包含密钥、凭证、个人数据、调试输出或与当前任务无关的生成文件。

## 2. 命名

标识符必须清楚表达其领域含义和职责。

- 优先使用目标语言生态中常见、可读的英文标识符。
- 已有项目采用稳定命名时，应保持一致，不得在局部变更中随意重命名。
- 涉及中国数术术语时，应在文档、类型说明或术语表中保留中文原名，并说明代码标识符与中文术语的对应关系。
- 拼音、意译或约定英文名都不是组织级强制方案；具体选择应由目标项目的术语规范决定。
- 缩写只用于领域内稳定且不会造成歧义的概念。

不得仅为了“统一风格”批量重命名与当前任务无关的公共符号。

## 3. 注释与文档

注释应解释代码本身无法清楚表达的原因、约束和权衡，而不是逐行复述实现。

以下内容通常需要说明：

- 非显而易见的算法选择；
- 精度、容差、单位和时间尺度；
- 数据来源与适用范围；
- 兼容性或历史原因；
- 临时方案的退出条件；
- 公共 API 的输入、输出、错误和边界行为。

已经过期的注释必须随代码一起更新或删除。

## 4. 类型、错误与边界

- 不得无故降低类型安全或绕过已有校验。
- 外部输入、文件、网络响应和持久化数据必须在边界处验证。
- 错误信息应帮助调用者定位问题，但不得泄露密钥、凭证或敏感数据。
- 不得用空 catch、无说明的默认值或静默失败隐藏异常。
- 精度、单位、时区、历法规则、流派和版本等会影响结果的前提应显式表达。

## 5. 依赖与公共接口

- 优先复用仓库已有依赖和能力，避免为小功能引入重量级依赖。
- 新增运行时依赖、公共 API 或数据格式前，应按照贡献指南先讨论。
- 公共接口应保持最小、稳定且可测试；内部实现不得因为方便而被无意导出。
- Breaking Change 必须明确标记，并说明受影响使用者和迁移方式。

## 6. 格式化与生成内容

- 格式由目标仓库的自动化工具决定，不进行无关的手工格式争论。
- 不得在功能变更中混入全仓库格式化，除非该格式化是当前任务的明确目标。
- 生成文件应由仓库明确说明是否提交、如何生成和如何验证。
- 修改生成源时，应同步更新需要版本控制的生成结果。

## 7. 语言与框架特定规则

Rust、TypeScript、Python、Web、移动端或其他技术栈的具体规则，应保留在使用该技术的仓库中，并尽可能通过配置和 CI 自动执行。

组织级文档不统一规定：

- 必须使用哪一种编程语言；
- 固定的目录结构；
- 所有仓库共同的 formatter 或 linter；
- 与项目实际技术栈无关的框架约束。

## 8. 评审检查

代码评审至少关注：

- 是否符合仓库职责和依赖边界；
- 命名和公共接口是否清晰；
- 正常路径、边界条件和错误路径是否正确；
- 测试是否能够发现回归；
- 文档是否与行为同步；
- 是否引入兼容性、安全、性能或长期维护风险。

## 9. 文件维护

本文件由 MathArts 组织维护者维护。出现以下情况时应当复审：

- 多个仓库反复出现相同的代码质量问题；
- 通用约定已经能够通过共享自动化执行；
- 术语命名策略形成独立的权威规范；
- 本文件开始与项目本地工具或语言惯例发生系统性冲突。
