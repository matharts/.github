# Commit 规范

MathArts 采用 [Conventional Commits](https://www.conventionalcommits.org/) 规范，并针对数术领域做了少量扩展。

## 格式

```
<类型>(<范围>): <简要描述>

[可选的详细说明]

[可选的脚注]
```

### 示例

```
feat(bagua): 实现先天八卦方位映射

基于《说卦传》原文，建立八卦与方位的标准映射关系。
乾南坤北、离东坎西，为伏羲先天方位。

Refs: #12
```

```
fix(tiangan): 修正天干五合化气的条件判断

甲己合化土需满足月令条件，此前缺少该校验。
```

```
docs(glossary): 补充"用神"在不同流派中的定义差异
```

## 类型

| 类型       | 含义   | 示例场景                          |
| ---------- | ------ | --------------------------------- |
| `feat`     | 新功能 | 新增六十四卦推演算法              |
| `fix`      | 修复   | 修正地支六冲的映射错误            |
| `docs`     | 文档   | 补充术语表、更新 README           |
| `refactor` | 重构   | 重新组织天干地支数据结构          |
| `test`     | 测试   | 补充排盘算法的单元测试            |
| `chore`    | 杂务   | 更新依赖、调整 CI 配置            |
| `style`    | 格式   | 代码格式化，不涉及逻辑变更        |
| `perf`     | 性能   | 优化大量数据的推演计算效率        |
| `ci`       | CI/CD  | 修改 GitHub Actions 配置          |
| `data`     | 数据   | 新增/修正典籍原文数据、术语映射表 |

`data` 是 MathArts 的扩展类型，用于区分"知识数据的变更"与"代码逻辑的变更"——在数术数字化项目中，这两者同等重要但性质不同。

## 范围

范围是可选的，用于标识改动所属的模块。各仓库自行定义有效范围，通常对应核心模块名称。

常见范围举例：

- `bagua` — 八卦相关
- `tiangan` — 天干相关
- `dizhi` — 地支相关
- `calendar` — 历法计算
- `glossary` — 术语表
- `engine` — 推演引擎

## 简要描述

- 使用中文，以动词开头，不加句号。
- 控制在 50 个字符以内。
- 说明"做了什么"，而不是"怎么做的"。

好的写法：

- `实现先天八卦方位映射`
- `修正天干五合化气的条件判断`
- `补充纳甲装卦的测试用例`

不好的写法：

- `更新了一些代码`
- `修改 bug`
- `添加一个新功能`

## 详细说明（可选）

与简要描述之间空一行。用于解释"为什么做这个改动"以及"背景信息"。如果涉及数术理论依据，建议简要注明出处（典籍名、卷章）。

## 脚注（可选）

- `Refs: #123` — 关联 Issue
- `BREAKING CHANGE: 描述` — 不兼容变更

## 一个 Commit 做一件事

每个 Commit 应该是一个独立的、可理解的改动。如果你发现自己在写 Commit 信息时用了"和"字连接两件不同的事，考虑拆成两个 Commit。
